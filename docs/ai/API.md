# Общий контекст фронтенда и бэкенда

Статус: REST API будет реализован на Django REST Framework и документирован OpenAPI через `drf-spectacular`. В проекте пока нет утверждённого OpenAPI-контракта и работающих endpoints. Этот документ не следует использовать как доказательство существования API.

## Как согласовать функцию

1. Найти сценарий в [DOMAIN.md](DOMAIN.md) и определить субъекта, право и область доступа.
2. Зафиксировать запрос, ответ, ошибки, изменение статуса и поведение повтора операции.
3. Описать контракт через `drf-spectacular` в OpenAPI и указать реальный путь к схеме здесь.
4. Фронт пишет адаптер/моки и типы по тому же контракту; бэк реализует валидацию и бизнес-операцию.
5. Проверить успешный сценарий, отказ в доступе, ошибки и повтор запроса на реальном API.

Пока контракт не создан, примерные пути и поля не считать утверждёнными. Технические соглашения выбирать совместно для обоих приложений.

## Минимальные договорённости

| Область | Что необходимо определить |
| --- | --- |
| Сессия | Тип субъекта adult/child, срок, завершение, CSRF при cookie-сессиях, поведение после истечения |
| Идентификаторы | UUID передавать строками; не путать account_id и child_id |
| Код ребёнка | Строка из шести цифр, включая ведущие нули |
| DTO | Отдельные модели чтения и записи; приватные поля доступны только целевым кабинетам |
| Имена полей | Единая договорённость snake_case/camelCase и место преобразования |
| Даты | Формат ISO 8601 с часовым поясом для времени; date рождения отдельно без смещения |
| Списки | Пагинация, сортировка и фильтры; не отдавать всю историю сообщений или попыток одним неограниченным ответом |
| Ошибки | Стабильный машинный код, понятное сообщение, ошибки полей; согласовать HTTP-статусы |
| Повторы | Идемпотентность для опасных повторных действий, время жизни ключа и ответ на повтор |
| Конкурентное редактирование | Проверка версии или иная стратегия, согласованная с правилами публикации |
| Файлы | Загрузка, проверка готовности, привязка, получение разрешённого URL, ошибки и срок доступа |
| Права | Разрешённые действия можно возвращать для UI; окончательная проверка всегда на сервере |

## Разные сущности — разные статусы

Это значения из модели, а не полная утверждённая диаграмма переходов:

| Сущность | Значения |
| --- | --- |
| tasks | draft / published / archived |
| child_tasks | accepted / submitted / under_review / rework / completed / declined |
| task_submissions.review_status | under_review / accepted / rework |

`accepted` у child_tasks означает «взято», у попытки — «работа принята». Успешный финал child_tasks называется `completed`. Не объединять эти enum в один общий тип.

Предпросмотр не создаёт child_tasks; повторяемость задания не означает возможность повторной сдачи с новой наградой в том же экземпляре. Различать новую попытку и новое взятие.

## Операции интеграции

Для первого сквозного контура нужны: вход взрослого/ребёнка, текущая сессия, продолжение онбординга, каталог/линия/диалог, предпросмотр и взятие задания, отправка попытки с файлами, очередь и результат проверки, сообщения взятого задания, характеристики, три подтверждения готовности и архивирование.

Текстовый ответ условному узлу требует отдельного решения: где сохраняется, как интерпретируется, что запускает переход и награду. Не использовать автоматически task_submissions или task_messages только потому, что обе таблицы содержат текст.

## Готовность интеграции

Экран на моках — готовый прототип интерфейса, но ещё не завершённая интеграция. Завершение означает проверенный запрос к реальному серверу, серверную проверку доступа и состояния, корректное обновление UI и отсутствие повторного начисления при повторе запроса.

## Передача между backend- и frontend-чатами

Backend владеет исходной OpenAPI-схемой. При изменении контракта в отчёте передаются: операция и метод, путь, auth/permissions, request/response DTO, коды ошибок, правила повтора и путь к обновлённой схеме. Frontend обновляет generated-типы одной воспроизводимой командой, затем адаптер, UI и тесты; generated-файл вручную не исправляется.

Если backend ещё не реализован, frontend может использовать mock только по явно записанному draft-контракту и помечает его как mock. Расхождения не решаются независимо двумя чатами: спорное поле или поведение фиксируется в этом документе либо `OPEN_QUESTIONS.md`, после чего обе стороны обновляются от одного решения.
