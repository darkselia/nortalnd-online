# Ориентиры для бэкенда

Источник бизнес-правил: [DOMAIN](DOMAIN.md), поля и логические описания: [schema.json](schema.json). Реализовывать на Django 6.1.1 + Django REST Framework по [STACK](STACK.md); следующие пункты не являются готовыми миграциями.

## Архитектура и модель

Используется один модульный Django-бэкенд с PostgreSQL и ответственностью по [M1–M8](MODULES.md). Схему меняют только миграции Django; модели, serializers, viewsets/API-views и сервисы бизнес-операций не смешивать в одном слое. Наличие поля в логической модели не означает, что для него уже определены индекс, default, unique, on_delete или окончательный enum.

Схема не описывает все механизмы продакшена: сессии, историю аудита, хранение текстовых ответов на условные узлы и версии контента ещё нужно спроектировать. Не объявлять 48 таблиц исчерпывающей физической схемой.

## Аутентификация и авторизация

Account и children — разные виды субъектов. Сессия должна явно различать их. Пользовательские id из тела запроса не подтверждают личность. При создании попытки ребёнок определяется по аутентификации и проверенному экземпляру задания.

Проверка сотрудника: активность → актуальное назначение → разрешение действия → область → конкретный объект. Проверять списки и detail/action endpoints, включая прямую подстановку чужого id. Для браузера пройти цепочку task → task_line → character.

Родитель получает данные только связанных детей; доступ к чату дополнительно требует can_view_browser_chat для этой пары. Для файлов проверяется доступ к исходной попытке/объекту, а не знание media_id. Хеши паролей и кодов не входят в API-ответы.

Шестизначный код требует ограничения перебора и безопасной смены. Ограничение запросов и сессии — отдельные инженерные задачи; штатная модель пользователя сама их не гарантирует.

## Операции, требующие согласованного изменения данных

| Операция | Условия и результат |
| --- | --- |
| Обработка оплаченной заявки | Проверка организатора; создание кабинетов и связей с защитой от повторной обработки |
| Открытие диалога | Проверить доступ к линии; записать первое знакомство ровно один раз; корректно вернуть первую реплику |
| Подтверждение готовности | Проверить соответствующую роль и область, сохранить автора/дату; публикация только при трёх подтверждениях и обязательных данных |
| Взятие задания | Проверить опубликованность и доступность; создать child_tasks только после действия ребёнка |
| Отправка попытки | Проверить владельца, состояние и вариант; сохранить новую попытку и допустимые файлы без перезаписи истории |
| Проверка работы | Проверить право браузера, переход статуса и обратную связь; успешное завершение и начисления согласованы |
| Отказ | Проверить допустимость перехода; учитывать отказ и экономическое последствие по согласованному правилу |
| Начисление | Сумма и тип выводятся из серверных правил; записать журнал и обновить производные кэши |

Использовать транзакции и ограничения БД там, где это обеспечивает инвариант. Одного reward_accrued недостаточно при двух конкурентных запросах. Выбрать и проверить стратегию идемпотентности/блокировок; ключ операции должен учитывать вид источника и конкретную награду, чтобы не запретить несколько законных начислений одного события.

Письма, уведомления и формирование файлов запускать после успешного сохранения операции через `transaction.on_commit`. Фоновые задачи выполняет Celery с Redis; повтор worker не должен повторять бизнес-эффект. Не переносить критичные переходы статусов и начисления в неявные Django signals.

## Целостность и особые ссылки

- Для составных PK сохранить уникальность пары. Внешние поля варианта должны ссылаться на вариант того же задания.
- tasks.workshop_id должен соответствовать мастерской task_line; текстовая модель не заменяет эту проверку.
- Ссылки `*_staff_account_id` обозначают аккаунт с staff_profiles, `parent_account_id` — с parent_profiles. Наличие профиля не заменяет ролевую проверку.
- `scope_id`, `sender_id`, `source_id` полиморфны. Допустимые пары «тип + объект» валидируются явно; не создавать обычный FK на случайно выбранную таблицу.
- Для начислений токенов workshop_id обязателен; для reputation обязателен character_id. NULL в SQL-типе не отменяет условной обязательности.
- Базовый узел имеет ключ line_id + node_type_id. Цели переходов нужно проверять в контексте линии.
- Историю попыток и начислений не удалять каскадом без продуманного правила хранения. Окончательное поведение удаления определить до миграций.

## API, файлы и наблюдаемость

Описывать бизнес-действия отдельно от произвольного изменения status через общий PATCH. Не принимать от клиента доверенные роли, автора проверки, сумму награды или факт публикации.

Загрузки отделять от сохранения попытки; проверять владельца загрузки, завершённость и допустимость использования файла. Ограничения размера/формата документировать и сообщать фронту. Медиа не становятся публичными автоматически после принятия работы.

Логировать технические идентификаторы операции и ошибки без паролей, кодов и содержимого детских сообщений. Полная модель аудита остаётся открытым вопросом Q11/Q15: явно спроектировать её при реализации соответствующей функции.

DRF — единственная точка публичного REST API; OpenAPI генерируется `drf-spectacular`. Закрытые медиа выдавать после проверки доступа через S3-совместимое хранилище, а не по постоянному публичному URL. Перед миграциями по спорной области проверить [OPEN_QUESTIONS](OPEN_QUESTIONS.md). Проверки прав, переходов и конкурентных начислений — в [CHECKS](CHECKS.md).
