# Нортландия онлайн — правила backend

Эти инструкции действуют для всей папки `backend/`. Общение и пояснения — на русском; код, модели и API — на английском по соглашениям Python/Django.

## Перед любой задачей

1. Прочитать [локальный контекст](docs/ai/CONTEXT.md).
2. Проверить реальные зависимости, настройки, миграции и команды — контекст описывает состояние, но не заменяет файлы проекта.
3. Для затронутого сценария найти модуль M1–M8 и открытый вопрос в локальном контексте. Он содержит обязательный минимум для автономной работы в этой IDE.

## Границы ответственности

- Django владеет бизнес-правилами, авторизацией, переходами статусов, начислениями, публикацией, доступом к файлам и схемой БД.
- DRF предоставляет REST API. OpenAPI генерируется через `drf-spectacular` и является контрактом для Nuxt; таблицы БД не являются DTO.
- Не менять frontend из backend-задачи без прямого запроса. Если меняется контракт, сначала изменить и проверить OpenAPI, затем описать требуемое изменение frontend в результате работы.
- Не придумывать продуктовые правила. Блокирующую неопределённость отметить с ID вопроса; независимую часть работы продолжить.

## Обязательные инварианты

- `Account` — взрослая учётная запись; ребёнок — отдельная сущность и отдельный субъект входа.
- Сотрудник может иметь несколько назначений ролей с областью и сроком. Одного поля `role` недостаточно.
- Персонаж связан с мастерской через линию, а не напрямую с единственным сотрудником или мастерской.
- Сервер проверяет право и scope как для списков, так и для detail/action endpoints.
- Пароли и шестизначные детские коды хранятся только как хеши и никогда не возвращаются API.
- Начисления, публикация и принятие работы выполняются транзакционно и идемпотентно. Не прятать их в Django signals.
- Файлы ребёнка закрыты; знание `media_id` или URL не даёт доступа.

## Стиль реализации

- Разделять модели хранения, serializers/DTO, permissions, selectors/queries и явные сервисы бизнес-операций.
- Схему менять только миграциями Django. До первой прикладной миграции создать собственный `AUTH_USER_MODEL`.
- Для FK, unique/check constraints, `on_delete`, индексов и enum сверяться со сценарием: логическая схема не определяет их автоматически.
- Избегать N+1, неограниченных списков и произвольного `PATCH status`; бизнес-действия оформлять отдельными endpoints.
- Побочные эффекты ставить в Celery через `transaction.on_commit`; повтор задачи не должен дублировать бизнес-эффект.
- Тестировать успешный путь, запрещённый доступ, невалидный переход и повтор/конкуренцию. Транзакционные проверки выполнять на PostgreSQL.

## Перед завершением

- Запустить только реально существующие линтеры и тесты, относящиеся к изменению.
- Для миграций выполнить `makemigrations --check` и проверить план миграции, когда команды будут настроены.
- Сообщить изменённые файлы, выполненные проверки, изменение API и оставшиеся ограничения.
- Не утверждать, что DRF, PostgreSQL, тесты или Celery подключены, пока это не подтверждено файлами проекта.

## Git-коммиты

- Агенты не создают прямые коммиты в `main`; изменения готовятся в короткоживущей feature-ветке для последующего pull request. Человек может коммитить в `main` вручную.
- Использовать Conventional Commits в формате `type(scope): subject`; `scope` обязателен и отражает область, например `backend`, имя Django app или доменный модуль.
- Допустимые `type`: `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`, `perf`, `style`.
- `subject` и body писать на английском в повелительном наклонении, без точки в конце. Breaking change помечать через `!` после scope и/или footer `BREAKING CHANGE:`.
- GPG/SSH-подпись не обязательна. Не смешивать в одном коммите несвязанные изменения.
