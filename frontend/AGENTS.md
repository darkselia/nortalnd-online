# Нортландия онлайн — правила frontend

Эти инструкции действуют для всей папки `frontend/`. Общение и пояснения — на русском; код, компоненты и типы — на английском по соглашениям Vue/Nuxt/TypeScript.

## Перед любой задачей

1. Прочитать [локальный контекст](docs/ai/CONTEXT.md).
2. Проверить реальные `package.json`, `nuxt.config.ts`, структуру `app/` и доступные npm scripts.
3. Для экрана определить пользователя, источник данных, разрешённые действия, состояния загрузки/пустоты/ошибки и соответствующий модуль M1–M8.
4. Для спорного поведения проверить список открытых вопросов в локальном контексте; не закреплять предположение в интерфейсе.

## Границы ответственности

- Nuxt отображает состояние и вызывает API. Права, переходы статусов, начисления, публикация и доступ к файлам окончательно проверяет Django.
- Не реализовывать второй backend в Nuxt server routes и не переносить туда бизнес-правила.
- Не менять backend из frontend-задачи без прямого запроса. Если контракт недостаточен, описать необходимый endpoint/поле/ошибку, не выдумывать их как существующие.
- Старые демонстрационные решения не являются архитектурой продукта: не переносить React-код, localStorage, демоданные и клиентские вычисления бизнес-правил.

## Компоненты и данные

- Nuxt UI использовать для форм, таблиц, модалок, меню и служебных кабинетов. Игровые сцены, реплики и карточки делать собственными Vue-компонентами на Tailwind.
- Компоненты держать небольшими; бизнес-сценарии собирать в composables, общий API-доступ — в одном typed client.
- Pinia использовать только для состояния, разделяемого между страницами/ветками UI. Серверные данные загружать через Nuxt и не создавать их независимые копии в stores без причины.
- Типы API получать из OpenAPI. Не выводить DTO из таблиц БД и не редактировать generated-типы вручную.
- Все персональные SSR-запросы учитывают cookies пользователя и не попадают в общий кэш.

## UX и безопасность

- Mobile-first; проверять длинные русские строки, системное увеличение шрифта, клавиатуру и фокус.
- Для запросов предусматривать loading, empty, error и retry; для мутаций — pending и безопасный повтор.
- Невидимая кнопка не является авторизацией. UI использует разрешённые действия из API, но сервер всё равно проверяет доступ.
- Детский код хранить и передавать строкой из шести цифр. Не хранить пароли, коды, финансовые итоги и игровые начисления в localStorage.
- Не вставлять пользовательский HTML. Закрытые медиа показывать только по разрешённому сервером временному URL.

## Проверки

- После изменения запускать существующие `npm run lint`, `npm run typecheck` и `npm run build` соразмерно риску.
- После подключения тестов Vitest покрывает компоненты/composables/stores/API-adapter, Playwright — критические сквозные сценарии.
- Сообщать, какие экраны работают на моках, а какие проверены с реальным Django API.
- Не заявлять о тестах или интеграции, которых ещё нет в `package.json`.

## Git-коммиты

- Агенты не создают прямые коммиты в `main`; изменения готовятся в короткоживущей feature-ветке для последующего pull request. Человек может коммитить в `main` вручную.
- Использовать Conventional Commits в формате `type(scope): subject`; `scope` обязателен и отражает область, например `frontend`, имя Nuxt-функции или доменный модуль.
- Допустимые `type`: `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`, `perf`, `style`.
- `subject` и body писать на английском в повелительном наклонении, без точки в конце. Breaking change помечать через `!` после scope и/или footer `BREAKING CHANGE:`.
- GPG/SSH-подпись не обязательна. Не смешивать в одном коммите несвязанные изменения.
