# Дорожная карта разработки

Этот файл фиксирует уже сделанную подготовку и показывает, что ещё нужно реализовать, чтобы получить готовый продукт. Этап — крупный результат развития продукта. Задача — самостоятельная единица работы, для которой можно составить отдельный план, добавить её в систему задач и учитывать затраченное время.

## Как пользоваться дорожной картой

Обозначения статуса:

- `[ ]` — не начато;
- `[~]` — выполняется;
- `[x]` — завершено.

Области задач:

- `[Решение]` — зафиксировать продуктовое или архитектурное решение до реализации;
- `[Backend]` — сервер, данные и API;
- `[Frontend]` — пользовательский интерфейс;
- `[Infra]` — окружение, доставка и эксплуатация;
- `[QA]` — автоматизированная или ручная проверка готового контура;
- `Qxx` — связанный вопрос из `docs/ai/OPEN_QUESTIONS.md`.

Номера M1–M8 — предметные модули документации.
Каждая задача ограничена одним слоем работы или одной связанной операцией и включает необходимые ей миграции, DTO, тесты и документацию. Отдельная QA-задача проверяет сквозной сценарий нескольких готовых задач.



## Состав MVP

- Семью принимают по телефону или в личных сообщениях; оформление остаётся вне сайта. Уполномоченный сотрудник создаёт аккаунты и семейные связи через закрытый интерфейс.
- Согласия на обработку данных ребёнка при ручном приёме получают и хранят вне системы по утверждённой процедуре. Онлайн-форма и реестр согласий не входят в MVP.
- Родитель и ребёнок входят в свои кабинеты. Родитель видит связанных детей, их разрешённые результаты и числовой прогресс.
- Ребёнок проходит онбординг, открывает мастерскую и диалог, в том числе настроенные сотрудником условные реплики, берёт и выполняет задание, получает отзыв и может общаться в чате взятого задания.
- Сотрудник создаёт мастерские, контентные ветки и задания и проверяет работы в отдельном кабинете сайта. Для публикации нужны три согласования: браузера, методиста и гейм-мастера.
- В MVP задания проверяет сотрудник; автоматическая проверка по эталонным ответам добавляется после выпуска. Сервер начисляет теги, токены мастерства и действия и репутацию по утверждённым правилам. Балансы и прогресс показываются без карты.
- Закрытые файлы, права и данные детей защищены; основные сценарии проверены и развёрнуты.

После MVP идут автоматическая проверка, публичные заявки семей и организаций, отдельное управление персоналом, сертификаты, подписки и онлайн-оплата, уведомления и дополнительные игровые функции. Django admin допускается для первичного создания сотрудников и технической поддержки. Полный список открытых правил — в `docs/ai/OPEN_QUESTIONS.md`.





# Часть I. Подготовка и MVP

## Этап 1. Подготовить инженерный фундамент

**Результат этапа:** монорепозиторий, документация, демонстрационный прототип и каркасы приложений и модель Account подготовлены; backend воспроизводимо запускается через Conda или venv, использует PostgreSQL и имеет базовые проверки качества.

- [x] **1.1 [Решение] Зафиксировать основу проекта** — описать назначение продукта, группы пользователей, утверждённый стек, ключевые бизнес-правила и границы модулей. Отдельно собрать нерешённые вопросы и подготовить общий контекст, чтобы разработка разных частей проекта опиралась на одни решения.
- [x] **1.2 [Infra] Собрать структуру монорепозитория** — разделить клиент, сервер, документацию и демонстрационные материалы на понятные области с собственными инструкциями. Настроить исключения Git для секретов, зависимостей, окружений, результатов сборки и локальных рабочих файлов.
- [x] **1.3 [Backend] Описать логическую модель данных** — сгруппировать сущности по предметным модулям и зафиксировать их ключи, поля, типы и связи в машиночитаемой схеме. Добавить проверку целостности схемы и пояснить, что она задаёт направление для будущих Django-моделей, но не заменяет миграции.
- [x] **1.4 [Frontend] Подготовить демонстрационный прототип** — собрать автономные примеры основных экранов и переходов, чтобы согласовывать внешний вид и пользовательские сценарии до интеграции. Проверить, что прототип открывается без сервера и не содержит сломанных локальных ресурсов.
- [x] **1.5 [Backend] Подготовить зависимости и Python-окружение** — разделить пакеты работающего приложения и инструменты разработки, закрепить версию Python и способ установки зависимостей. Обеспечить одинаковый набор пакетов для Conda и venv, чтобы production не зависел от Conda.
- [x] **1.6 [Backend] Создать стартовый backend-каркас** — создать Django-проект, вынести конфигурацию в окружение и подключить основу REST API и документации контракта. Проверить запуск сервера и административной части, не добавляя прикладные сущности раньше проектирования модулей.
- [x] **1.7 [Infra] Настроить локальную PostgreSQL** — добавить воспроизводимый запуск базы в Compose, постоянное хранение данных и проверку готовности контейнера. Подключить Django через переменные окружения и проверить миграции и реальное соединение без резервного перехода на SQLite.
- [x] **1.8 [Backend] Настроить качество Python-кода** — определить единые правила lint и форматирования для выбранной версии Python. Добавить воспроизводимые команды и привести стартовый backend-код к состоянию, в котором обе проверки проходят.
- [x] **1.9 [QA] Настроить тестовый контур backend** — подключить pytest к Django и определить расположение тестов и настройки запуска. Добавить технические проверки конфигурации и отдельной тестовой PostgreSQL, исключив работу тестов с локальной рабочей базой.
- [x] **1.10 [Frontend] Создать стартовый frontend-каркас** — создать Nuxt-приложение и подключить утверждённые библиотеки интерфейса, типизации и состояния. Проверить локальный запуск и production-сборку до начала разработки прикладных страниц.
- [x] **1.11 [Frontend] Определить архитектуру состояния frontend** — разделить ответственность между серверной загрузкой Nuxt, повторяемой логикой composables и общим клиентским состоянием Pinia. Зафиксировать правила в документации, чтобы новые функции не создавали дублирующие источники данных.
- [x] **1.12 [Frontend] Настроить качество и тесты frontend** — подключить lint, проверку TypeScript и тестовый runner с едиными npm-командами. Проверить инструменты на стартовом приложении и оставить содержательные компонентные тесты задачам, в которых появится реальный интерфейс.
- [x] **1.13 [Infra] Подключить общие Git hooks** — хранить hooks в репозитории и дать разработчику одну команду для их включения в новом клоне. Перед коммитом проверять затронутую часть проекта, а перед push — полный обязательный набор проверок.
- [x] **1.14 [Infra] Документировать установку и запуск проекта** — описать последовательность первоначальной настройки, запуск базы и приложений, миграции и команды качества. Привести отдельные варианты для Conda и venv и явно отделить локальную разработку от будущего production-развёртывания.


## Этап 2. Подготовить общую основу API и интерфейса

**Результат этапа:** для первого прикладного модуля готовы правила API, простая оболочка Nuxt, общий клиент Django API с техническим прокси и основа тестов. Подключение реальных endpoints входа и генерация DTO остаются в этапе 3. Эти задачи не требуют заранее создавать модели остальных модулей.

- [x] **2.1 [Backend] Спроектировать границы Django-приложений** — определить владельцев моделей и направление зависимостей. Использовать подготовленную структуру при добавлении законченных модулей.
- [x] **2.2 [Backend] Создать кастомную модель Account** — использовать созданный взрослый аккаунт, менеджер, admin и начальную миграцию как основу модуля пользователей.
- [x] **2.3 [Backend] Закрепить общие правила API и OpenAPI** — определить префикс версии, формат ошибок и способ описывать сессии, затем добавить команду проверки OpenAPI. DRF и drf-spectacular уже подключены; реальные DTO, пагинацию и фильтры проверить вместе с первыми endpoints семейного модуля.
- [x] **2.4 [Frontend] Создать минимальную оболочку и дизайн-токены** — заменить starter-экран простой русскоязычной основой, установить базовые цвета, типографику, отступы и состояния интерактивных элементов через Tailwind и Nuxt UI. Реализованы отдельные шапка/футер, локальные изображения и общие токены светлой/тёмной темы с переключателем Nuxt UI.
- [x] **2.5 [QA] Подготовить окружение компонентных тестов** — Vitest дополнен Nuxt Test Utils, Vue Test Utils и Happy DOM; настроены рендер в окружении Nuxt, автоматическое размонтирование и команды запуска. Постоянные тесты добавлять вместе с функциями.
- [x] **2.6 [Frontend] Подготовить общий клиент Django API и прокси Nuxt** — предоставить методы запросов через `useNuxtApp().$api` с результатом `ok`; проксировать `/api/...` на закрытый backend origin. Сохранять контракт Django, cookies и контекст пользователя при SSR; перед изменением данных читать актуальный CSRF. Добавить транспортные тесты отдельно от Nuxt-проверок и инструкции использования с `useAsyncData`. Получение первого CSRF и реальные endpoints подключить в 3.12.


## Этап 3. Пользователи, семьи и права сотрудников (M1 + M2)

**Результат:** уполномоченный сотрудник создаёт семью, родитель видит связанных детей, ребёнок входит в свой кабинет. Модели родителей, детей и их связи создаются вместе; общая основа этапа 2 используется в первом работающем модуле.

- [ ] **3.1 [Решение] Утвердить правила создания семьи и детского логина** — определить, кто создаёт семью, как связывается уже существующий взрослый и как разрешаются совпадения логинов детей (Q03, Q16, Q18). Записать правила и примеры до изменения моделей.
- [ ] **3.2 [Решение] Утвердить внешнее оформление согласий при ручном приёме** — описать, кто получает и хранит документы вне системы, как до выдачи реквизитов подтверждается выполнение процедуры и что происходит при отзыве. Не проектировать для MVP онлайн-форму и реестр согласий; юридические формулировки утвердить отдельно.
- [ ] **3.3 [Решение] Утвердить восстановление и отзыв доступа** — решить, как сбрасывают пароль взрослого и код ребёнка, передают реквизиты и отключают аккаунт (Q02). Для MVP описать конкретный ручной или автоматизированный сценарий без предположения о готовых SMS и почте.
- [ ] **3.4 [Backend] Создать модели ребёнка, родителя и семейной связи** — добавить обе сущности и связь с типом родства в одной группе миграций. Проверить нескольких взрослых у ребёнка, уникальность связи, ограничения удаления и сохранение закрытых данных.
- [ ] **3.5 [Backend] Создать профиль сотрудника и роли** — связать служебный профиль с Account, создать роли и разрешённые действия. Первого технического администратора создавать через `createsuperuser`, следующих сотрудников в MVP — через Django admin. Проверить, что взрослый может иметь родительский и служебный профили без смешения прав.
- [ ] **3.6 [Backend] Реализовать назначения и проверку прав** — хранить область, срок и отзыв назначения; применять проверку действия и объекта. Поддержать начальную выдачу назначений в Django admin, записывать выдачу и отзыв в аудит и тестировать истёкшие и чужие права. Связи с мастерскими добавить после создания мастерских. **Создать основу аудита критичных действий** — определить единый формат записи автора, действия, объекта, времени и безопасного контекста. Дать модулям явный способ записывать события без секретов и содержимого детской переписки; проверить неизменяемость истории обычным пользователем. Конкретные события подключать в задачах использующих модулей.
- [ ] **3.7 [Backend] Реализовать вход и выход взрослого** — поддержать телефон или добавленный email с паролем, получение текущего профиля и выход. Проверить cookies, CSRF, отключённый аккаунт и защиту от перебора.
- [ ] **3.8 [Backend] Реализовать вход и выход ребёнка** — использовать отдельного ребёнка как субъект сессии и шестизначный код как строку с ведущими нулями. Хранить хеш кода; проверить неверный код, перебор и запрет взрослого API.
- [ ] **3.9 [Backend] Реализовать закрытое создание семьи** — добавить endpoint создания взрослого, ребёнка и связи или привязки к существующему взрослому после разрешения по процедуре 3.2. Проверить роль сотрудника, выполнять действия транзакционно, предотвращать дубли и записывать событие в аудит без секретов.
- [ ] **3.10 [Backend] Реализовать просмотр и изменение семейных связей** — сотруднику предоставить списки и карточки семей и разрешённые изменения, родителю — только собственных детей. Проверить прямые запросы чужого ID, состав DTO и аудит служебных изменений.
- [ ] **3.11 [Backend] Реализовать восстановление и отключение доступа** — выполнить утверждённые в 3.3 операции сброса реквизитов и отзыва доступа. Проверить полномочия, завершение сессий и сохранение истории без записи секретов в журнал.
- [ ] **3.12 [Frontend] Подключить API пользователей, получение CSRF и генерацию типов** — использовать клиент и прокси из 2.6. Создать воспроизводимую генерацию TypeScript-типов из прикладной OpenAPI-схемы. Первую часть выполнять после готовности взрослого входа 3.7, совместно с формой 3.14; endpoints детского входа и семей подключать по мере готовности соответствующего backend. Пути, DTO и получение первого CSRF брать из готового контракта. Проверить на настоящем Django API получение CSRF, вход, текущую сессию, выход, неверные реквизиты, перезагрузку страницы и изоляцию двух пользователей при SSR; сетевые ошибки обрабатывать без автоматического повторения изменяющих запросов.
- [ ] **3.13 [Frontend] Создать layouts и навигацию кабинетов** — подготовить отдельные зоны родителя, ребёнка и сотрудника поверх общей оболочки этапа 2. Показывать только доступные разделы, обрабатывать отсутствие сессии и проверить переход между кабинетами взрослого с несколькими профилями.
- [ ] **3.14 [Frontend] Создать форму входа взрослого** — реализовать телефон/email, пароль, выход и переход в доступный кабинет. Проверить неверные реквизиты, истёкшую сессию и повторную загрузку страницы.

- [ ] **3.17 [Frontend] Создать управление семьями и доступом** — показать сотруднику список и карточку семьи, изменение связей и разрешённые операции 3.11. Проверить подтверждение отключения и отсутствие отображения сохранённых секретов.
- [ ] **3.18 [Frontend] Создать базовый кабинет родителя** — показать связанных детей и переключение выбранного ребёнка. Проверить пустое состояние и чужого ребёнка; данные заданий и прогресса подключить после их реализации.

## Этап 4. Закрытые файлы и метки (M7)

**Результат:** следующие модули могут загружать закрытые файлы и использовать общий справочник меток.

Проверить записи критичных действий, отсутствие секретов и текста детской переписки в аудите и выполнение политики хранения и удаления; выявленные нарушения исправить и перепроверить.
- [ ] **9.4 [QA] Проверить удобство экранов** — пройти клавиатурой и на мобильных ширинах вход, кабинеты, формы и чат. Исправить блокирующие ошибки и перепроверить сценарии.
- [ ] **9.5 [QA] Измерить основные запросы** — проверить каталог, очереди и историю на реальных объёмах. Устранить N+1 и добавить обоснованные индексы и лимиты.
- [ ] **9.6 [QA] Автоматизировать сквозной путь** — расширить Playwright-сценарий до создания условной реплики, её показа ребёнку, публикации задания, выполнения, проверки и единственной награды. Обеспечить чистые тестовые данные и диагностику ошибок.
- [ ] **9.7 [Infra] Настроить CI** — запускать lint, typecheck, тесты, сборку и проверку OpenAPI с нужными сервисами. Проверить успешный проход и остановку при ошибке.
- [ ] **9.8 [Infra] Развернуть тестовую среду** — поднять Nuxt, Django, PostgreSQL и закрытое хранилище с отдельными секретами. Проверить миграции, рестарт и сквозной путь.
- [ ] **9.9 [Infra] Настроить диагностику сервисов** — добавить healthchecks и сбор ошибок без секретов. Проверить обнаружение сбоя web, базы и хранилища.
- [ ] **9.10 [Infra] Настроить резервные копии** — сохранять БД и закрытые файлы вне рабочего сервера. Выполнить пробное восстановление в отдельную среду.
- [ ] **9.11 [Infra] Подготовить рабочую среду** — настроить домен, TLS, секреты и процессы по проверенной тестовой среде. Проверить миграции, готовность и план отката.
- [ ] **9.12 [QA] Провести приёмку MVP** — пройти согласованный чек-лист трёх кабинетов, базового и условного диалога, публикации, ручной проверки, чата и наград. Зафиксировать дефекты и подтвердить отсутствие блокирующих.
- [ ] **9.13 [Infra] Выпустить MVP** — после отдельного решения о выпуске доставить проверенную версию и выполнить миграции. Проверить вход, задание, решение проверяющего и начисление в рабочей среде.

# Часть II. Развитие после MVP

Эти функции не блокируют первый выпуск. Порядок модулей после MVP можно изменить по обратной связи, но внутри каждого соблюдается зависимость: правила → модели → операции и API → интерфейс → проверка. Таблицы из логической схемы создаются вместе с использующим их модулем.

## Этап 10. Автоматическая проверка заданий

**Результат:** опубликованное задание с поддерживаемым форматом ответа проверяется по эталонам без решения сотрудника; неподдерживаемые форматы остаются на ручной проверке.

- [ ] **10.1 [Решение] Утвердить правила автоматической проверки** — определить поддерживаемые форматы, сравнение ответа с эталоном, исход при несовпадении и возможность доработки. Записать примеры, в том числе пустой ответ и повторную отправку; не считать любой файл пригодным для автопроверки.
- [ ] **10.2 [Backend] Добавить эталоны и автоматический тип задания** — создать связанные с версией задания эталонные ответы, валидацию формата и настройку типа проверки. Запретить публикацию автоматического задания без достаточных данных и не менять уже взятые версии.
- [ ] **10.3 [Backend] Реализовать проверку отправленной попытки** — сравнивать ответ по правилу 10.1, сохранять результат и переводить статусы в одной операции. При успешном результате вызвать существующий сервис начисления; проверить повтор запроса и конкуренцию без второго решения или награды.
- [ ] **10.4 [Frontend] Добавить автопроверку в конструктор задания** — дать сотруднику выбор поддерживаемого типа и редактирование эталонов с понятными ошибками публикации. Не показывать автоматическую проверку для неподдерживаемых форматов.
- [ ] **10.5 [Frontend] Показать ребёнку результат автопроверки** — подключить утверждённые состояния успеха, несовпадения и доработки к существующей карточке задания. Проверить повторную отправку и обновление страницы.
- [ ] **10.6 [QA] Проверить автоматическую и ручную ветки** — покрыть совпадение, несовпадение, пустой ответ, повтор и неизменность старых попыток. Проверить, что ручное задание по-прежнему попадает в очередь сотрудника.

## Этап 11. Онлайн-заявки семей

**Результат:** семья может подать заявку на сайте, а сотрудник провести её через договор и ручное подтверждение оплаты до создания кабинетов. Ручной приём остаётся доступным.

- [ ] **11.1 [Решение] Утвердить сценарий семейной онлайн-заявки** — определить данные заявителя и детей, статусы договора и оплаты, согласия, срок хранения данных заявки и связь с уже созданной семьёй. Отделить отправку формы от регистрации и от будущей онлайн-оплаты.
- [ ] **11.2 [Backend] Создать семейную заявку и историю статусов** — сохранить данные до создания кабинетов по выбранной модели, установить ограничения и политику хранения чувствительных сведений. Проверить дубли, неизменность обработанного снимка и допустимые переходы.
- [ ] **11.3 [Backend] Реализовать публичную отправку семейной заявки** — валидировать поля и защищать endpoint от повторов и злоупотребления. Возвращать понятный результат без разглашения существующих аккаунтов.
- [ ] **11.4 [Frontend] Создать публичную форму заявки семьи** — реализовать заявителя и список детей, ошибки полей и подтверждение отправки. Проверить добавление нескольких детей и повтор клика.
- [ ] **11.5 [Backend] Реализовать обработку семейной заявки** — предоставить сотруднику очередь и переходы «договор отправлен → ожидание оплаты → оплата подтверждена → кабинеты созданы» либо отказ по утверждённой схеме. Вызывать готовое создание семьи только после разрешённого перехода, проверять полномочия и повтор обработки.
- [ ] **11.6 [Frontend] Создать очередь семейных заявок** — показать сотруднику состав заявки, историю, статусы и разрешённые действия. Проверить подтверждение рискованных операций и обновление после решения другого сотрудника.
- [ ] **11.7 [QA] Проверить семейный онлайн-приём** — пройти форму, договор, ручное подтверждение оплаты и создание семьи. Проверить дубли, чужой доступ, срок хранения данных заявки и сохранение ручного способа приёма.

## Этап 12. Управление персоналом через сайт

**Результат:** организатор управляет сотрудниками и их назначениями через служебный кабинет, сохраняя Django admin для первоначальной настройки и поддержки.

- [ ] **12.1 [Решение] Утвердить управление служебными аккаунтами** — закрыть оставшуюся часть Q03: кто создаёт и отключает сотрудника, кто выдаёт роли и как одобряется второй профиль взрослого по Q16. Определить, какие операции остаются только у технического администратора.
- [ ] **12.2 [Backend] Создать API управления сотрудниками** — предоставить разрешённые списки, карточки, создание и изменение служебного профиля. Проверять право на каждую операцию и не раскрывать закрытые данные и реквизиты чужих сотрудников.
- [ ] **12.3 [Backend] Создать API управления назначениями** — дать выдачу, окончание и просмотр активных и прежних ролей с объектной проверкой области. Записывать изменения в аудит и не позволять повышать собственные полномочия обходным запросом.
- [ ] **12.4 [Frontend] Создать список и карточку сотрудника** — показать профиль, состояние и разрешённые действия, добавить форму создания или изменения. Проверить ошибки, пустой список и прямой переход к недоступной карточке.
- [ ] **12.5 [Frontend] Создать управление ролями сотрудника** — показать область и срок назначения, историю и действие отзыва. Проверить выбор допустимого объекта, подтверждение отзыва и отказ при недостаточных правах.
- [ ] **12.6 [QA] Проверить управление персоналом** — пройти создание сотрудника, выдачу, истечение и отзыв назначения через кабинет. Проверить чужую область, попытку самоповышения и записи аудита.

## Этап 13. Организации, когорты и подключение классов

**Результат:** школа или партнёр подаёт заявку на сайте; сотрудник оформляет организацию и группу, подключает детей, а куратор видит только свою область.

- [ ] **13.1 [Решение] Утвердить институциональный приём и согласия** — закрыть Q12 для полномочий представителя, согласий на данные детей, договора и ручной оплаты. Разграничить семейную связь, организационное представительство и роль куратора до создания аккаунтов.
- [ ] **13.2 [Backend] Создать организацию и когорту** — добавить тип и состояние организации, учебный период и состояние группы, связь ребёнка с когортой и необходимые области назначений. Проверить историю перехода между группами и сохранение семейных связей; не дублировать без решения текущую связь `children.cohort_id`.
- [ ] **13.3 [Backend] Реализовать API управления группами** — предоставить разрешённые списки организаций, когорт и их состава и операции изменения. Проверить сроки полномочий куратора, прямые запросы чужой организации и переход ребёнка между группами.
- [ ] **13.4 [Backend] Реализовать публичную заявку организации** — расширить заявки этапа 11 данными представителя, организации и нескольких детей. Валидировать отправку без взрослой сессии, защитить endpoint от злоупотребления и дублей и не раскрывать сведения о существующих аккаунтах.
- [ ] **13.5 [Backend] Реализовать обработку заявки организации** — добавить служебную очередь и переходы договора, ручной оплаты и решения по утверждённому процессу. Проверить область сотрудника, повтор решения и запрет создания кабинетов до разрешённого состояния.
- [ ] **13.6 [Backend] Реализовать подключение участников организации** — из одобренной заявки создать или связать аккаунт уполномоченного взрослого и детские аккаунты, назначить детям институциональный источник и когорту и подготовить безопасную выдачу реквизитов. Проверить дубли, повтор операции, полномочия представителя и сохранение имеющегося прогресса.
- [ ] **13.7 [Frontend] Создать публичную форму заявки организации** — дать представителю ввод организации, контакта и списка детей, ошибки по полям и подтверждение отправки. Проверить повтор клика и отсутствие публичного доступа к чужой заявке.
- [ ] **13.8 [Frontend] Добавить обработку заявок организаций** — показать отдельную очередь, состав и историю заявки, решения сотрудника и связь с созданной организацией и когортой. Проверить полномочия и изменение статуса после обработки.
- [ ] **13.9 [Frontend] Создать кабинет организации и куратора** — показать разрешённые группы и детей, формы изменения состава и состояние подключения. Не подменять организационные права семейной связью; проверить пустые и запрещённые состояния.
- [ ] **13.10 [QA] Проверить подключение класса** — пройти заявку, договор, подтверждение оплаты, создание группы и детских аккаунтов и выдачу доступа куратору. Проверить согласия по утверждённому процессу, чужие группы, отзыв полномочий и сохранение прогресса.

## Этап 14. Сертификаты и первая фоновая задача

**Результат:** достигший порога ребёнок получает сертификат, который формируется вне HTTP-запроса и скачивается только уполномоченным пользователем.

- [ ] **14.1 [Решение] Утвердить правила и хранение сертификата** — закрыть Q09: порог, шаблон, реквизиты, повторную выдачу и доступ к файлу. Выбрать хранение в `child_workshops` либо отдельной записи выдачи и синхронизировать решение с логической схемой.
- [ ] **14.2 [Backend] Создать данные о выдаче сертификата** — реализовать выбранную в 14.1 модель с ребёнком, мастерской, порогом, шаблоном, состоянием и ссылкой на закрытый файл. Проверить ограничения, миграции и сохранение истории при перевыпуске.
- [ ] **14.3 [Infra] Подключить Redis и Celery для сертификатов** — настроить брокер, worker, очередь, timeouts, retry и диагностику вместе с реальным потребителем 14.4. Проверить запуск и восстановление после перезапуска, не добавляя расписание без потребности.
- [ ] **14.4 [Backend] Реализовать фоновый выпуск и скачивание** — после commit проверять порог, ставить генерацию в очередь, сохранять её состояние и выдавать закрытую ссылку после успеха. Проверить повтор запроса, повтор доставки и сбой генерации без второго сертификата.
- [ ] **14.5 [Frontend] Создать раздел сертификатов** — показать достигнутые и будущие сертификаты, статус формирования и скачивание. Проверить пустое состояние, ожидание и ошибку файла.
- [ ] **14.6 [QA] Проверить сертификаты и сбои worker** — проверить достижение порога, повтор выдачи, остановку и перезапуск worker и восстановление после сбоя. Подтвердить доступ ребёнка и связанного родителя и запрет скачивания чужого файла.

## Этап 15. Уведомления кабинета

**Результат:** значимые события обучения видны адресату в кабинете; дополнительные каналы доставки подключаются только по утверждённому сценарию.

- [ ] **15.1 [Решение] Определить события и получателей уведомлений** — выбрать события задания, проверки и сертификата, аудиторию, срок хранения и каналы. Не смешивать индикатор непрочитанного результата MVP с полноценным центром уведомлений.
- [ ] **15.2 [Backend] Создать уведомления и API кабинета** — хранить получателя, тип, связанный объект и статус прочтения; предоставить список и отметку о прочтении. Проверить изоляцию данных и уже недоступный объект.
- [ ] **15.3 [Backend] Подключить события к уведомлениям** — создавать запись только после успешной бизнес-операции и не дублировать её при повторе. Если утверждён внешний канал, использовать существующий worker и отдельное правило повторной доставки без дублей.
- [ ] **15.4 [Frontend] Создать центр уведомлений** — показать непрочитанные события, переход к доступному объекту и отметку о прочтении. Проверить пустое состояние, ошибку сети и исчезнувший объект.
- [ ] **15.5 [QA] Проверить доставку и изоляцию уведомлений** — проверить повтор события, чужого получателя, отзыв доступа к связанному объекту и временный сбой внешнего канала, если он подключён.

## Этап 16. Подписки и онлайн-оплата

**Результат:** оплаченный период определяет доступ ребёнка, но истечение не удаляет аккаунт, работы и прогресс.

- [ ] **16.1 [Решение] Утвердить финансовую модель** — закрыть Q14: тарифы, покупателя семьи или организации, покрываемых детей, сроки, оплату, отмену и продление. Выбрать провайдера и юридический сценарий до интеграции.
- [ ] **16.2 [Backend] Создать планы и подписки** — добавить тариф, период, покупателя и связь с покрываемыми детьми, сохранив условия покупки в истории. Проверить состояния, ограничения и независимость семейной связи от подписки.
- [ ] **16.3 [Backend] Реализовать ограничения доступа по подписке** — применять активный период к утверждённым платным действиям. Проверить истечение и восстановление без удаления прогресса и без обхода через прямой API-запрос.
- [ ] **16.4 [Backend] Подключить платёжный сервис** — создать платежи и обработку подписанных webhook; связывать внешний платёж с периодом, не доверяя браузерному возврату. Проверить повторы, задержки и события не по порядку.
- [ ] **16.5 [Frontend] Создать интерфейс подписки и оплаты** — показать тариф, срок, покрываемых детей и состояние платежа, предоставить разрешённые действия. Проверить ожидание, отказ и продление.
- [ ] **16.6 [QA] Проверить оплату и доступ** — проверить неверную подпись, повтор webhook, истечение, продление и единственность финансового эффекта для семьи и организации.

## Когда задача считается завершённой

Для каждой задачи проверяются её результат и соответствующие ему ошибки и права. При изменении данных добавляются миграции и тесты, при изменении API — DTO и OpenAPI, при изменении интерфейса — тесты поведения и проверка основных состояний. Описанные в задаче проверки входят в неё, а не становятся отдельным неопределённым этапом.

Этап считается завершённым, когда его пользовательский сценарий проходит через интерфейс и сервер с реальными данными и проверенными связями. Исключение — этапы подготовки и выпуска, где результат сформулирован отдельно.
