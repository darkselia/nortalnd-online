# Запросы к Django

Общий клиент доступен как `useNuxtApp().$api` и использует встроенный `$fetch`. Примеры ниже условные: прикладные endpoints и DTO подключаются на этапе 3.

## Настройка прокси

Создайте локальный `frontend/.env` по `frontend/.env.example` и задайте `NUXT_BACKEND_ORIGIN=http://127.0.0.1:8000`. В production переменная задаётся в окружении процесса Nuxt. Адрес содержит только origin, без `/api`, реквизитов, query и fragment; он находится в закрытом runtimeConfig и не передаётся браузеру.

Браузер обращается к `/api/...` на адресе сайта. Nuxt передаёт запрос Django через H3 `proxyRequest`, сохраняя путь, query, метод, тело, статус, cookies и отдельные Set-Cookie. Исходные Host, Origin и Referer сохраняются: Django должен принимать адрес сайта в своих настройках проверки Host и CSRF. Прокси не следует переадресациям и не кэширует ответы. При отсутствии корректной настройки возвращается 503; при недоступности Django — 502. В сообщениях нет внутреннего адреса и stack trace. Собственного ограничения времени ожидания у прокси нет.

## Методы и результат

`request<T>(path, options)` и короткие `get`, `post`, `put`, `patch`, `delete` принимают путь относительно `/api/v1/`, например `examples/`. Завершающий `/` сохраняется; внешние адреса и выход из префикса запрещены. Query передаётся отдельным объектом.

Options содержат `query`, `body`, `headers` и `signal`; у `request` есть также `method`, по умолчанию GET. Собственного timeout у клиента нет; отменить запрос можно через AbortSignal. Автоматические повторы и HTTP-переадресации отключены. JSON-объекты сериализует `$fetch`; для FormData Content-Type формируется автоматически.

- Успех: `{ ok: true, status, data, pagination? }`. Клиент разворачивает Django-оболочку `{ data }` и сохраняет pagination. Данные имеют тип `T | null`; для 204 возвращается null без разбора тела. Пустой список, false, 0 и пустая строка не превращаются в ошибку.
- Ошибка: `{ ok: false, status, error: { kind, code, message, fields } }`. Без HTTP-ответа status равен null. Различаются HTTP, сеть, отмена, некорректный ответ, некорректный запрос и отсутствие CSRF.
- Backend-коды и ошибки полей сохраняются, включая вложенные имена и `non_field_errors`. Отсутствие взрослой сессии — 403 / `not_authenticated`; ошибки валидации — `validation_error`. Неструктурированные ответы и технические сообщения серверных ошибок заменяются нейтральным текстом.

Клиент не открывает экран ошибок, не показывает уведомления и не переводит на вход. Компонент сам решает, что показать по результату `ok`.

Клиент проверяет основную оболочку ответа, но доверяет контракту Django для содержимого pagination и ошибок полей. `requestApi` выполняет запрос и нормализует результат; `createApiClient` только связывает fetch текущего приложения с короткими методами. Подробная runtime-валидация DTO не добавлена.

## Загрузка и обновление

Используйте `useAsyncData`, чтобы Nuxt управлял загрузкой и передавал SSR-результат браузеру без повторного запроса при гидратации:

```ts
const { $api } = useNuxtApp()

const { data: result, status, refresh } = await useAsyncData(
  'example-list',
  (_nuxtApp, { signal }) => $api.get<{ id: string }[]>('examples/', {
    query: { page: 1 },
    signal,
  }),
)
```

Пока `status.value === 'pending'`, показывайте загрузку. Если `result.value?.ok`, используйте `result.value.data` и pagination; иначе покажите `result.value?.error.message`. Пустой список и null обрабатывайте отдельно от ошибки. Кнопка повтора или успешное изменение данных вызывают `refresh()`.

HTTP-ошибка API находится в результате `ok: false`, а не в `error` самого `useAsyncData`: обработчик успешно вернул нормализованный результат. Ключ выбирайте по ресурсу и параметрам запроса; общий серверный кэш для персональных страниц не включайте.

## Изменение данных и CSRF

POST, PUT, PATCH и DELETE вызывайте из браузерных обработчиков:

```ts
const { $api } = useNuxtApp()

async function save() {
  const result = await $api.post<{ id: string }>('examples/', {
    body: { name: 'Анна' },
  })
  if (!result.ok) {
    // Показать result.error.message и result.error.fields в форме.
    return
  }
  await refresh()
}
```

Перед каждым изменяющим запросом клиент читает актуальный `csrftoken` из cookies и добавляет X-CSRFToken. Если токена нет, возвращается локальная ошибка `csrf_missing`, запрос не отправляется. Получение первого токена появится вместе с backend-контрактом входа; клиент не придумывает endpoint для этого.

На SSR плагин использует `useRequestFetch()` с контекстом текущего пользователя и исходным Host. Экземпляр `$api` принадлежит конкретному Nuxt-приложению: cookies и результаты не сохраняются в глобальных переменных. Чтение выполняйте через `useAsyncData`, а изменяющие операции оставляйте браузерным обработчикам.
