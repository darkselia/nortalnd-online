# Контекст backend «Нортландии онлайн»

Этот файл самодостаточен для IDE, открытой только на `backend/`. Личные сведения об окружении находятся в необязательном `docs/local/ENVIRONMENT.md`, исключённом из Git.

## Текущее состояние

### Границы MVP — решение от 2026-09-29

Приём семьи и оформление выполняются вне сайта. На сайте уполномоченный сотрудник создаёт аккаунты родителей и детей и семейные связи; публичной регистрации и API заявок в MVP нет. Модуль пользователей реализуется вместе со связями, ролями, операциями, сессиями и проверками.

Обязательны кабинеты родителя и ребёнка, мастерские, диалоги, выполнение и чат задания, числовые награды и прогресс. Создание веток и заданий, три согласования и проверка работ выполняются через отдельный Nuxt-кабинет с Django API. Django admin используется для начального создания сотрудников и поддержки. Организации, когорты, сертификаты, автоматизация оплаты и карта отложены. Формулы и неутверждённые права остаются вопросами Qxx; порядок реализации находится в корневом ROADMAP.md.

### Реализованная основа

- Есть Django-проект, admin endpoint и приложение `accounts` с кастомным взрослым `AUTH_USER_MODEL`. Детская модель, профили взрослых и сотрудников ещё не созданы.
- `settings.py` читает `backend/.env` через `django-environ`. Версионируемый шаблон — `backend/.env.example`; локальный `.env` исключён из Git. Для разработки PostgreSQL 16 запускается сервисом `postgres` из корневого `compose.yaml`, а Django подключается через `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST` и `POSTGRES_PORT` без единой строки подключения.
- Утверждённая версия проекта — Django 6.1.1 на Python 3.13. Перед запуском Python-команд проверить interpreter PyCharm. `requirements.txt` содержит зависимости работающего приложения, а `requirements-dev.txt` добавляет pytest, pytest-django и Ruff. `environment.yml` устанавливает dev-набор при создании Conda-окружения; в уже активированном Conda или venv зависимости устанавливаются через `python -m pip install -r requirements-dev.txt`.
- Новое Conda-окружение по `environment.yml` называется `nortland-backend`. Фактические версии выбранного interpreter нужно сверять с requirements перед запуском; проверка версий не заменяет проверку БД, миграций и тестов.
- PostgreSQL — единственная настроенная БД. Контейнер запускается из корня репозитория командой `docker compose --env-file backend/.env up -d --wait postgres`; данные остаются в volume. Django запускается локально через `python manage.py runserver`.
- DRF и `drf-spectacular` подключены: схема настроена по `/api/schema/`, Swagger UI — по `/api/docs/`. Общий контракт будущих endpoints под `/api/v1/` задаёт оболочки ответов и ошибок, пагинацию, фильтры и безопасные настройки доступа; прикладных endpoints, фоновых задач и S3 storage пока нет. Существующий набор pytest покрывает отдельную тестовую PostgreSQL, взрослый Account и базовый API-контракт. Example endpoints из `tests/test_api.py` доступны только в тестовом URLConf.
- Git-репозиторий находится уровнем выше, в `nortland-online/`.

## Целевой стек

Python 3.13, Django 6.1.1, Django REST Framework, PostgreSQL через Psycopg 3, `django-environ`, `drf-spectacular`, Celery + Redis, `django-storages` + S3/MinIO. Проверки: pytest, pytest-django, factory-boy, coverage, Ruff, mypy + django-stubs. Gunicorn и reverse proxy относятся к развёртыванию, а не к локальному `runserver`.

## Доменные модули

| ID | Будущее Django app | Основные сущности и ответственность |
| --- | --- | --- |
| M1 | `accounts` | взрослые, дети, семьи, организации, когорты, заявки, согласия и онбординг |
| M2 | `staff` | профили сотрудников, назначения ролей, permissions, scope и сроки |
| M3 | `workshops` | мастерские, персонажи, линии, узлы диалога и условия |
| M4 | `tasks` | шаблоны заданий, варианты, материалы, награды и три согласования публикации |
| M5 | `submissions` | взятые задания, попытки, проверка, вложения и чат |
| M6 | `economy` | журнал начислений, кэши характеристик, репутация, сертификаты и инвентарь |
| M7 | `resources` | закрытые медиа и общий справочник меток |
| M8 | `subscriptions` | предварительная модель тарифов и оплаченного доступа; требования не завершены |

`accounts` — первое существующее доменное app; остальные создаются по порядку вместе с моделями и сценариями. `staff` появится при реализации персонала. Все 48 логических таблиц распределены по M1–M8 в общей карте `docs/ai/MODULES.md`.

Account представляет только взрослого. Для него обязателен уникальный телефон в международном формате; 11-значный ввод с началом `7` или `8` сохраняется как `+7`. Необязательный email также служит идентификатором парольного входа и уникален без учёта регистра. Nullable-поля `phone_verified_at`, `email_verified_at` и `external_brand_id` есть в модели, но подтверждение контактов и внешняя интеграция ещё не реализованы. Первый технический администратор создаётся через `createsuperuser`, а сотрудников на этапе MVP он заводит через Django admin. Флаг `is_staff` даёт доступ к Django admin и не заменяет будущие назначения ролей в `staff`. OAuth и SMS, восстановление доступа, родительский/детский онбординг и отправка реквизитов ещё не реализованы. Q02 и Q03 остаются частично открытыми; для детского логина см. Q18.

Зависимости направлены от потребителя к владельцу данных: `staff → accounts`, `resources → accounts`, `workshops → accounts/resources`, `economy → accounts/workshops/resources`, `tasks → accounts/staff/workshops/resources/economy`, `submissions → accounts/staff/workshops/tasks/resources/economy`, `subscriptions → accounts`. Это допустимые направления, а не обязательные импорты. Проверяющий права `staff` не импортирует модели всех остальных apps; доступ к файлу сначала проверяет владелец задания или попытки. Операции, затрагивающие несколько apps, координируются явными сервисами без встречных импортов и Django signals.

## Критические правила

- MVP: приём и оформление семьи вне сайта → после разрешения и подтверждения оплаты уполномоченный сотрудник создаёт взрослый и детский кабинеты и семейные связи. Публичные заявки отложены; родитель не создаёт ребёнка сам.
- Родитель видит только связанных детей. Чат закрыт по умолчанию и открывается отдельным разрешением для пары родитель–ребёнок.
- Браузер создаёт задания в линиях своего персонажа. Публикация требует готовности браузера, методиста и гейм-мастера плюс обязательные материалы; архивирует организатор.
- Просмотр задания не создаёт `child_task`; экземпляр появляется только после действия «Взять».
- Доработка создаёт новую попытку, старая попытка и её файлы сохраняются.
- `accruals` — источник истины экономики. Токены относятся к мастерской, репутация — к паре ребёнок–персонаж; кэши производны.
- Первое знакомство фиксируется для пары ребёнок–персонаж один раз. Выбор первой/повторной реплики нельзя определять после записи даты в том же запросе.

## API-соглашения

- Базовый префикс прикладных endpoints: `/api/v1/`; схема — `/api/schema/`, документация — `/api/docs/`. Окончательные операции появляются только вместе с OpenAPI-схемой.
- UUID передаются строками, даты-время — ISO 8601 с timezone, детский код — строка из шести цифр.
- В ответах использовать отдельные read/write serializers. Не отдавать хеши, служебные поля и чужие закрытые данные.
- Успех с телом: `{"data": <DTO>}`; список: `{"data": [...], "pagination": {"page": 1, "page_size": 20, "count": 0, "next": null, "previous": null}}`. `204` без тела. Размер страницы по умолчанию 20; положительный целый `page_size` выше 100 ограничивается до 100, нецелый или неположительный даёт `400`. Сортировка и фильтры задаются явно. Ошибки: `{"error": {"code": "...", "message": "...", "fields": {}}}`.
- Cookie-сессии требуют HttpOnly, Secure в production, SameSite и CSRF. Сессия явно различает взрослого и ребёнка.
- Опасные повторные действия имеют ключ/ограничение идемпотентности; блокировка кнопки на фронте не является защитой.
