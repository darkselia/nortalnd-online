# Утверждённый стек и поставка

Статус: актуализировано решением пользователя от 2026-09-14. Этот файл фиксирует технические границы реализации; он не объявляет отсутствующие зависимости или инфраструктуру установленными.

## Архитектура

Начинать с модульного монолита в одном Git-репозитории: один Nuxt-клиент, один Django API, одна PostgreSQL и чёткие доменные модули M1–M8. Модули — границы кода, а не микросервисы. Общий контракт API документируется OpenAPI и генерируется бэкендом.

```text
frontend/  Nuxt 4 application
backend/   Django project and domain apps
infra/     Compose, reverse proxy and deployment configuration
docs/      общий контекст, API и логическая схема для ИИ
```

Папки `frontend/` и `backend/` созданы и открываются в отдельных JetBrains IDE. Поэтому в каждой хранится локальный `AGENTS.md` и краткий контекст для автономного чата; общие требования остаются каноническими и не должны расходиться с локальными копиями.

## Backend

| Назначение | Решение |
| --- | --- |
| Язык и фреймворк | Python 3.13 и Django 6.1.1 |
| HTTP API | Django REST Framework |
| Контракт | `drf-spectacular`, OpenAPI 3; Nuxt получает типы из опубликованной схемы |
| Основная БД | PostgreSQL 16+ через `psycopg` |
| Конфигурация | `django-environ`; секреты только в окружении/менеджере секретов, не в Git |
| Фоновые работы | Celery + Redis: письма, уведомления, генерация сертификатов, обработка медиа; `django-celery-beat` — только когда появятся расписания |
| Файлы | `django-storages` + S3-совместимое хранилище; локально допустим MinIO; доступ к приватным файлам проверяет API |
| Продакшн-процесс | Gunicorn за Nginx или Caddy; ASGI/Channels добавлять только при подтверждённой потребности в WebSocket |
| Качество | pytest, pytest-django, factory-boy, coverage, Ruff, mypy + django-stubs, pre-commit |

Использовать свой `AUTH_USER_MODEL` с первой миграции. `Account` и `children` остаются разными субъектами входа согласно [DOMAIN.md](DOMAIN.md). Сложные операции оформлять явными сервисами и Django-транзакциями; не прятать начисления, публикацию и права в сигналах. Django admin допустим для внутренних справочников и поддержки, но не заменяет Nuxt-кабинеты.

## Frontend

| Назначение | Решение |
| --- | --- |
| Основа | Node.js 24 LTS, Nuxt 4, Vue 3, TypeScript в строгом режиме |
| Стили | Tailwind CSS; цвета, размеры и типографика — дизайн-токены проекта |
| Состояние | Pinia для действительно общего клиентского состояния; серверные данные не дублировать без причины |
| Компоненты кабинетов | Nuxt UI: формы, таблицы, модалки, меню и служебные кабинеты |
| Игровой UI | Собственные Vue-компоненты поверх Tailwind; Nuxt UI не должен диктовать сцену и карточки |
| Контракт API | единый API-клиент, типы из OpenAPI (`openapi-typescript` или эквивалент); не копировать таблицы БД в DTO |
| Проверки | Vitest для unit/component/composable/store; Playwright для сквозных браузерных сценариев |

Для приватных страниц не кэшировать персональные SSR-ответы совместно между пользователями. Аутентификация использует защищённые HttpOnly cookie-сессии, CSRF-защиту и один внешний origin: `/` — Nuxt, `/api` — Django. Конкретные endpoints, DTO и жизненный цикл сессии фиксируются в [API.md](API.md), а не выводятся из моделей.

## Git и Docker

Выбран исходный вариант — **один монорепозиторий**. Он удобнее, пока команда общая, а функции почти всегда меняют Nuxt, Django, OpenAPI и документацию одновременно. Использовать `main`, короткоживущие feature-ветки, pull request и CI с отдельными задачами для затронутых путей. Два репозитория оправданы позднее только при независимых командах, правах доступа или циклах выпуска; тогда OpenAPI и общие правила должны быть вынесены в версионируемый контракт.

Django и Nuxt локально запускаются обычными процессами, а PostgreSQL 16 — сервисом `postgres` из корневого Docker Compose. Это не требует отдельной установки PostgreSQL в ОС и сохраняет данные в именованном volume. Redis и MinIO следует добавлять в Compose вместе с использующим их кодом. В production контейнеризовать Nuxt, Django web и Celery worker; `beat` добавлять при расписании. На одном небольшом сервере достаточно Docker Compose, reverse proxy с TLS, отдельного хранилища секретов и регулярных проверяемых резервных копий PostgreSQL. Kubernetes на старте не нужен.

Docker сам по себе не является развёртыванием: перед staging/production нужны миграции как отдельный контролируемый шаг, health checks, журналы и мониторинг ошибок, ограничение доступа к Redis/PostgreSQL, S3-политики, TLS и проверка восстановления из бэкапа. В production предпочтительна управляемая PostgreSQL; при self-hosted БД её данные хранятся в постоянном volume и резервируются вне сервера.

## Что не добавлять заранее

- Микросервисы, Kubernetes, WebSocket/Channels, платёжный провайдер и поисковый движок — только после подтверждённых требований.
- Второй сервер бизнес-логики в Nuxt server routes: бизнес-правила, права и транзакции живут в Django.
- Публичные URL для детских файлов, секреты в `.env` в Git и SQLite как тест единственной production-схемы.
