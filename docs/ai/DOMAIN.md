# Предметная область и правила

Это самостоятельное описание предметной области для разработки. Предварительные и противоречивые места перечислены в [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md).

## Словарь

| Термин | Значение |
| --- | --- |
| Account | Взрослая учётная запись; может одновременно иметь parent_profiles и staff_profiles |
| Ребёнок | Отдельная сущность children, вход по логину и шестизначному коду |
| Браузер | Сотрудник, создающий контент и проверяющий работы от лица персонажа; не веб-браузер |
| Персонаж | Игровая личность; связан с мастерской через линию |
| Линия | Контентная последовательность в мастерской с ведущим персонажем |
| Задание | tasks — шаблон; child_tasks — конкретное взятие ребёнком |
| Попытка | task_submissions — одна отправка результата; предыдущие попытки сохраняются |
| Метки | labels — классификатор контента; не валюта |
| Теги | Игровая валюта в журнале начислений |
| Токены | Мастерства или действия; обязательно относятся к мастерской |
| Репутация | Отношение конкретного персонажа к ребёнку; общий показатель производный |

## Доступ и приём — блок 1

- Первый этап: публичная заявка → организатор отправляет договор и инструкции оплаты → подтверждает оплату → создаёт взрослый и детский кабинеты → передаёт реквизиты. Для организации заявка содержит данные нескольких детей.
- Родитель не создаёт ребёнка самостоятельно. Связь семьи, оплата и учётная запись — разные понятия. Истечение доступа не удаляет прогресс.
- У ребёнка несколько связанных взрослых; relation_type сохраняет mother / father / guardian / school_representative.
- Переписка недоступна родителю по умолчанию; право выдаётся по запросу для конкретной пары родитель–ребёнок. Связь с ребёнком сама по себе не разрешает чтение чата.
- Настоящее ФИО закрыто. В игровой части используется display_name. Коды и пароли не хранятся открытым текстом.
- У сотрудника несколько назначений роли с областью и сроком. Проверяются действие, конкретный объект, область и актуальность назначения.

## Мастерские и диалог — блок 2

- Цепочка контента: workshop → task_line → task. Персонаж определяется через task_line.character_id; один персонаж может встречаться в разных мастерских.
- Основной персонаж карточки мастерской не заменяет ведущего персонажа конкретной линии.
- Базовые узлы: start, hello, place, learn, hard, reward, offer, refuse, later. Тексты относятся к линии; браузер не изменяет произвольно базовый граф.
- Сцена состоит из фона линии и фигуры персонажа выбранного узла.
- Знакомство фиксируется при первом открытии диалога для пары ребёнок–персонаж. Первый показ использует обычный start, повторные могут использовать repeat_intro_text. Не выбирать повторную реплику только потому, что дата уже записана текущим запросом.
- Условные узлы доступны только при выполнении условия. Начальные формы ответа — кнопка и текстовое поле; правила обработки текстового ответа ещё требуют уточнения.

## Задания и выполнение — блоки 3–4

- Браузер создаёт черновики в линиях своего персонажа. Публикация автоматическая после готовности браузера, методиста и гейм-мастера и проверки обязательных материалов, включая видео. Архивирует организатор.
- task_dialogues хранит изменяемые реплики отдельного задания/линии; task_materials хранит общие материалы и материалы вариантов через nullable variant_id.
- Предпросмотр не создаёт child_tasks. Принятие создаёт экземпляр; новое разрешённое взятие повторяемого задания — новый экземпляр.
- Отправка результата создаёт новую попытку. Несколько файлов связываются через submission_media.
- Проверка хранит «что получилось» и при доработке «что доработать». Персональный отзыв, шаблонная реплика и свободное сообщение чата — разные сущности.
- Чат относится к уже взятому заданию. Предварительный вопрос до принятия и общий чат не спроектированы.

## Экономика — блок 5

- accruals — источник истины для изменения ресурсов. Балансы и кэши пересчитываются из журнала.
- Токены обоих типов принадлежат мастерской; награды заданий используют её task_token_type. Репутационное начисление относится к персонажу.
- Порог токенов мастерства даёт сертификат направления; детали выдачи и хранения нужно уточнить перед реализацией сертификатов.
- Начальная репутация 0 и диапазон -5…+5 записаны как предварительное решение. Первые два учитываемых отказа без штрафа; третий и последующие снижают репутацию ведущего персонажа. Период, сброс счётчика и точные параметры требуют решения.
- Повторная доставка запроса или выполнение фонового задания не должны дублировать награду. Клиент не присылает доверенную сумму начисления.

## Будущие возможности

Полные лента/блог, карта/экспедиции, лавка, предметы, платежи, общий чат и система модерации не считаются спроектированными только потому, что в схеме или прототипе есть задел. Объём конкретной реализации определяется задачей пользователя.
