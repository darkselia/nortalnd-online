# Ориентиры для фронтенда

Прочитать [STACK](STACK.md), [DOMAIN](DOMAIN.md), [MODULES](MODULES.md) и [OPEN_QUESTIONS](OPEN_QUESTIONS.md). Стек интерфейса утверждён: Nuxt 4, TypeScript, Tailwind CSS, Pinia и Nuxt UI; маршруты и готовый API пока не существуют.

## Визуальная и интерфейсная модель

- Детское приложение — иллюстрированное, mobile-first: мастерские, персонажи, диалоговые сцены, карточки заданий, карта и бейдж.
- Сцена диалога объединяет фон линии, фигуру текущего персонажа, реплику и доступные ответы. Она не должна выглядеть как стандартная административная форма.
- Служебные кабинеты организатора, методиста, браузера и гейм-мастера — функциональные формы, таблицы, фильтры, статусы и модальные подтверждения на Nuxt UI.
- Игровые компоненты создаются специально для проекта на Vue и Tailwind. Nuxt UI используется там, где важны типовое поведение, клавиатура и управление фокусом.
- Цвета, типографику, отступы, скругления и состояния оформлять как дизайн-токены. Стандартный Nuxt starter не 
  является утверждённым дизайном.з

## Экран → данные → действие

| Экран | Данные и поведение |
| --- | --- |
| Публичная заявка | Семья/организация, контакт и дети; отправка заявки без регистрации |
| Вход | Отдельные формы взрослого и ребёнка; код ребёнка — строка из шести цифр с сохранением ведущих нулей |
| Онбординг | Серверное состояние шага и завершения; повторный вход продолжает сценарий |
| Мастерские | Категории, метки, поиск, карточки и прогресс; основной персонаж карточки |
| Диалог | Конкретная линия, её фон, фигура текущего узла, обычный/повторный start, доступные условные ответы |
| Задание | Предпросмотр, материалы, видео, форма ответа, действие «Взять» |
| Выполнение | Экземпляр child_tasks, текущий статус, история попыток, несколько файлов, доработка |
| Чат | Сообщения конкретного взятого задания; отдельное разрешение родителя |
| Бейдж | Серверные характеристики и история; клиент не начисляет токены |
| Кабинет команды | Авторский черновик, три независимых подтверждения готовности, архивирование организатором, проверка работ |

## Компоненты и состояние — предложение

Отделять сцену `CharacterScene`, реплику `DialogueBubble`, карточку `WorkshopCard`, ответ `TaskAnswerForm`, список попыток и чат. Названия примерные; адаптировать к реальному приложению.

Постоянные данные загружать через единый API-слой. Открытие модального окна, выбранный файл до загрузки и положение панели обычно локальны. Глобальный store использовать для действительно общего состояния, избегая нескольких независимых копий одних серверных данных.

Использовать Nuxt 4 и TypeScript в строгом режиме. Данные загружать средствами Nuxt через единый API-слой; после мутаций явно обновлять состояние. Pinia оставлять для действительно общего UI-состояния, а Nuxt UI применять для форм, таблиц, модалок и кабинетов; игровые сцены делать собственными Vue-компонентами на Tailwind. При приватном SSR не допускать общего кэша персональных ответов. Способ сессии и передачи cookies определить в общем контракте.

Для каждого запроса предусмотреть загрузку, пустой результат, ошибку и повтор. Для действий — состояние отправки и повтор после сетевого сбоя. Блокировка кнопки уменьшает двойные клики, но серверная идемпотентность всё равно необходима.

Права из API определяют видимость кнопок; прямой API-запрос дополнительно проверяет сервер. Не хранить финансовые или игровые итоги как доверенный localStorage. Не вставлять произвольный HTML из текстового ответа ребёнка.

## Проверка интерфейса

- Мобильная компоновка имеет приоритет; проверить также широкий экран, длинные русские тексты и системное увеличение шрифта.
- Формы имеют подписи и понятные ошибки; диалоги доступны с клавиатуры, фокус возвращается после закрытия.
- Неудачное выполнение и отказ описываются нейтрально, без давления на ребёнка.
- Несколько файлов показываются отдельно, с прогрессом/ошибкой загрузки; состояние попытки не теряется при отказе одного файла.
- Награда, статус публикации и отзыв меняются после подтверждения сервера. Неподключённые экраны явно используют mock-адаптер и не объявляются интегрированными.

Vitest проверяет компоненты, composables, stores и API-адаптеры; Playwright — критические пользовательские сценарии в браузере. Конкретные команды появятся вместе с `frontend/package.json`.

До появления реального API реализовывать моки по согласованному контракту из [API.md](API.md). API-адаптер должен позволять заменить моки без переписывания компонентов.
